# v0.2 连续采集与算法接口

本次输出只送中控台，默认不写图像或结果文件，不控制 PLC / 剔除机构。中控台自身的调试日志仍保存在电脑上。

## 已实现与未验证

- 已实现：一次启动、多块接收、一次停止；有界队列；并行接收与处理；错误传播；超时和缓冲区所有权；结构化结果输出；中控台显示与离线回放。
- 已实现：CPU 灰度统计后端、PL 用户态适配器、PL 驱动 ABI 约定、可供 HLS 使用的 AXI memory 图像统计参考模块。
- 尚未实现：实际 PL 内核驱动、Vivado 中的互连与地址分配、设备树、FPGA bitstream 集成，以及你的正式图像检测算法。
- 尚未验证：真实连续 Camera Link / PCIe DMA、板上线程调度与吞吐量、HLS RTL 综合与时序、真实 FPGA 运算。
- 回放记录来自合成像素的软件运行，不是相机数据。

## 软件数据路径

```text
SG3000 帧头与 DMA
  -> sg_stream_begin / sg_stream_next / sg_stream_end
  -> 图像块所有权移交至有界队列
  -> 工作线程调用 processor.process(image_view, timeout, result)
  -> result_sink.publish(image_view, result, timeout)
  -> SGJSON 串口输出
  -> 电脑中控台
```

sg_stream_begin 只发送一次采集启动；sg_stream_next 不启停采集；退出时统一 sg_stream_end。每个图像块仍按卡提供的帧头边界组织，目前不改变采集卡的宽度/高度配置。

默认队列深度 4，最大单块 16 MiB。内存上限按“队列 + 接收中 1 块 + 处理中 1 块”估计为 96 MiB，所有配置要求这个上限不超过 512 MiB。缓冲区只有在处理和结果发布返回后才释放。队列满会以 ENOBUFS 停止，不覆盖旧块，也不声称没有丢线。

收到图像块后，接收线程可继续收下一块；处理线程计算上一块。底层 SG3000 DMA 仍使用原有同步 64 KiB 分块和轮询接口，不是新实现的中断式多描述符 DMA。持续运行逻辑不等于已经达到相机最高行频。

## 数据连续性

块内包号、偏移和完整长度仍严格检查。跨块编号的真实演进尚无有效相机数据支持，所以默认 observe：观察“是否为前一编号 + 1”，记录异常但不推算丢了几行。可显式选择 strict，在此假设不满足时停止。两种模式均不宣称物理连续性已验证。

`sequence` 是本次软件会话接收的序号；`card_block_id` 是卡提供的编号；`received_line_start` 是此前收到的行数，不是输送带编码器位置。`received_ns` 是主机单调时钟下的接收完成时间，不是曝光时间。32/64 位编号的含义不能混用。

## 算法接口

见 `core/sg_processing.h`。image_view 包含：像素指针、字节数、width/height/stride、Mono8 格式、软件序号、卡编号、累计行偏移、接收时间和来源/连续性标志。

process 是同步、限时接口。传入像素是借用的，只在调用期间有效。返回时处理器必须不再访问该指针，失败也一样；异步硬件后端应在内部等待完成，超时后确认停止或隔离其内核缓冲区。不能把 malloc 地址直接交给硬件当物理地址。

结果包含 ABI、序号、行偏移、算法标识、状态/错误、decision 以及当前参考统计字段。CPU stats 和 HLS 参考模块都只做灰度统计，decision 必须为 unknown。正式检测算法应另行定义缺陷类型、位置与置信度，必要时扩展并升级 ABI；当前不猜测这些语义。

## FPGA 对接路线

参考模块采用 AXI4 memory 图像输入和结果输出，AXI4-Lite 配置尺寸、阈值和编号。PS 收到图像后，未来的 PL 驱动负责将图像放入 PL 可访问的 DMA 缓冲区、同步缓存、启动 IP、等待完成、取回结果。这样可先保留 SG3000 接收链路，再接入 PL 算法。

`fpga/sg_image_stats.cpp` 是可交给 HLS 的参考 C++ 模块；其 C 模型已测试，未宣称已综合或时序通过。结果数组固定 10 个 uint64：magic/ABI、序号、行偏移、像素数、灰度和、超过阈值的像素数、最小值、最大值、错误位、算法 ID。阈值统计不等于缺陷。

`core/sg_pl_uapi.h` 定义待实现的 Linux 字符设备 `/dev/sg_imageproc`：GET_CAPS 确认版本和容量，PROCESS 同步提交一块图像。用户态适配器 `sg_pl_linux.c` 已有版本/能力查询、尺寸检查与返回值校验，但目前不存在匹配的 PL 内核驱动。选择 PL 时应明确失败，不回退到 CPU 假装硬件成功。

HLS 的 AXI memory 和 AXI4-Lite 接口依据 [AMD HLS interface 文档](https://docs.amd.com/r/2022.2-English/ug1399-vitis-hls/pragma-HLS-interface)。未来若改成视频 AXI4-Stream，要单独增加内存到视频流的桥接：视频协议的 TUSER0 是块/帧起始，TLAST 是行末，不能直接把通用 DMA 的包尾当作行末。参见 [AMD UG934 信号定义](https://docs.amd.com/r/en-US/ug934_axi_videoIP/AXI4-Stream-Signaling-Interface)。本版没有把 AXI memory 与视频 AXI4-Stream 混接。

## 输出协议与中控台

每行以 `SGJSON ` 开头，后接 schema=1 的 JSON。事件分 started、preflight、result、ended。64 位序号、时间、累计计数用十进制字符串，避免浏览器整数精度损失。结果格式见 interfaces/result-v1.schema.json。

处理每块都调用一次结果发布接口；当前中控台只按默认 1 秒周期采样显示 unknown 灰度测量值，processed_total 仍累计所有处理块。将来的 pass/fail 结果不走这个测量采样分支。串口输出阻塞超过限定时间会导致会话错误，不无限卡住接收。

单块结果在整次会话结束前不能证明停止成功。必须结合 ended 中的 error、stop_error、received、processed、编号异常数与队列满次数判断。没有 ended 标记时状态未知。回放会始终标为 recorded-replay，不替换硬件连接状态。

## 部署到现有 SD

保留原 SD 的所有文件。把 `board/sg3000-stream-v0.2.zip` 解压到 SD 根目录，新增 `sg3000-stream-v0.2/sg3000-stream` 和 SHA256SUMS。它不会替换原来 sg3000-linux-20261023 里的单帧程序和已验证驱动。

回实验室后，先按原流程检查板卡、加载基础接收程序。然后点击「加载连续程序」，只读挂载 SD、校验新包、拷入 /tmp。再选择 30 秒和 CPU 灰度统计，开始连续接收。期间可点中断；确认 ended.stop_error=0 后才知道程序报告正常停止。程序和新功能尚需首次上板验证。

命令示例：
```sh
./sg3000-stream --source hardware --processor stats --seconds 30
./sg3000-stream --source hardware --processor stats --seconds 0
./sg3000-stream --source synthetic --processor stats --max-blocks 10 --emit-ms 1
```

最后一条是合成数据测试，不访问采集卡。当前电脑不接板时，可在中控台直接点「离线结果回放」，查看已保存的软件测试结果。
